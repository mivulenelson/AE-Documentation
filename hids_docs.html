Autoencoder HIDS Sentinel Console

This guide explains how to install, start, and use the Autoencoder HIDS Sentinel Console. It is written as a practical guide for someone who wants to run the project without having to read the internal implementation first.

Documentation Quick Start Local Setup Docker Configuration Dashboard Endpoints Troubleshooting

What the system does

The system monitors network traffic on a selected network interface. It collects traffic information, extracts behavioral features from network flows, and uses the trained autoencoder model to identify activity that differs from normal traffic.

When the system identifies an unusual flow, the event can be stored in the SQLite database and displayed in the Sentinel Console. The dashboard also provides alert history, forensic information, model information, analyst feedback, and report generation.

Quick start

The quickest way to start the project is with Docker. Before starting, make sure the trained model files are available.

Requirements

  • Ubuntu 22.04 or a newer Ubuntu release is recommended.
  • Docker 20.10 or newer.
  • Docker Compose version 2.
  • An X11 display when using the graphical dashboard through Docker.
  • The trained autoencoder model file.
  • The trained scaler file.

Required model files

The project expects the following files in the model directory.

models/baseline_ae.keras
models/scaler.pkl

Start with Docker

From the project directory, make the Docker launch script executable and start the system. 

chmod +x docker/run.sh
./docker/run.sh

The launch process prepares the Docker environment, checks the model files, prepares the required configuration, allows the graphical dashboard to access the local display, and starts the system.

Running locally

Local execution is useful when developing or testing the project directly on Ubuntu. The original project uses Python 3.12 for its local environment.

Step 1: Create the environment

python3.12  -m venv env

Step 2: Activate the environment

source env/bin/activate

Step 3: Install the project requirements

pip install -r requirements.txt

Step 4: Make sure the model files exist

models/baseline_ae.keras
models/scaler.pkl

After the environment and model files are ready, start the backend and dashboard using the project's normal local startup commands.

The exact local startup command can depend on the project files currently present in your working copy. The original documentation confirms the dashboard entry point as the dashboard application and the backend as the FastAPI service.

Running with Docker

Docker provides the recommended way to run the complete application. The project contains a backend service and a graphical dashboard service.

Normal graphical operation

docker compose --env-file docker/.env --profile gui up --build

The graphical mode starts the backend and dashboard together.

Backend only

docker compose --env-file docker/.env --profile backend up --build

Backend only mode is useful when you only need the API or when the machine does not have a graphical desktop available.

Development mode

docker compose --env-file docker/.env --profile dev up --build

Development mode uses live project mounts so changes can be tested without rebuilding everything after every source change.

Docker display requirement

The graphical dashboard uses the host display. On a normal Ubuntu desktop the display is normally available through X11. The dashboard container therefore needs access to the local display socket. 

xhost +local:docker

The Docker launch process described by the original project documentation handles this as part of its normal startup procedure.

Configuration

The backend uses configuration values for the database, trained model, scaler, detection threshold, API port, and logging level.

Setting Purpose
DATABASE_URL Location of the SQLite database used by the system.
HIDS_MODEL_PATH Location of the trained autoencoder model.
HIDS_SCALER_PATH Location of the fitted feature scaler.
HIDS_THRESHOLD_CONFIG Location of the detection threshold configuration.
API_PORT Port used by the backend API. The documented default is 9000.
LOG_LEVEL Controls the backend logging level.
HOST_SITE_PACKAGES Location of the local environment packages when the Docker setup uses the host environment.
HIDS_API_URL Backend address used by the dashboard.
GUI_THEME Dashboard theme. The documented default is dark.
DISPLAY Display used by the graphical dashboard.
QT_QPA_PLATFORM Qt display platform. The documented X11 value is xcb.

Dashboard

The dashboard is the main place where an analyst can observe the system and inspect detected activity.

Console Grid

The main console shows current alerts and previous alert information. It also provides summary information such as the number of alerts, threat rate, and the latest event. A live signal chart displays reconstruction error over time.

Packet Ingestion

This page allows the analyst to select a network interface and observe system telemetry. It also displays the network feature information collected from traffic.

Model Analysis

This page displays model information including accuracy information, false positive information, and the current detection threshold. It also provides the retraining function described by the original project.

Alert History

The alert history page allows the analyst to inspect stored alerts. An alert can be opened to view its feature information, reconstruction error, destination address, protocol information, and analyst feedback.

Forensic Reports

The reports page provides summary information about recorded events and can generate a structured text report containing incident information and anomalous flows.

Settings

The settings page provides controls for the dashboard theme, network interface, detection threshold, and feature reference information.

Network detection information

The system extracts 22 behavioral values from TCP and UDP network flows. These values are used by the trained model when calculating the anomaly score.

Feature Purpose
flow_durationTotal duration of the network flow.
fwd_iat_meanAverage forward packet arrival interval.
fwd_iat_stdVariation in forward packet arrival intervals.
fwd_iat_minShortest forward packet arrival interval.
fwd_iat_maxLongest forward packet arrival interval.
fwd_iat_totalTotal forward packet arrival interval.
fwd_pkt_len_meanAverage forward packet length.
fwd_pkt_len_stdVariation in forward packet length.
fwd_pkt_len_minSmallest packet length in the flow.
fwd_pkt_len_maxLargest packet length in the flow.
total_fwd_bytesTotal forward traffic bytes.
flow_pkts_per_secPackets transferred per second.
flow_bytes_per_secBytes transferred per second.
pkt_len_varianceVariation in packet lengths.
burst_ratioAmount of time associated with burst traffic.
active_time_ratioAmount of the flow duration containing active traffic.
pkt_countTotal number of packets.
unique_ttl_countNumber of different TTL values observed.
ttl_meanAverage TTL value.
tcp_flag_ratioRatio of TCP control flag packets.
has_udpIndicates whether UDP traffic is present.
has_tcpIndicates whether TCP traffic is present.

API endpoints

The backend API is documented on port 9000. These are the endpoints listed in the original project documentation.

Method Endpoint Purpose
GET /ready Checks whether the model is loaded and the database is accessible.
POST /capture/start Starts packet capture on the selected interface.
POST /capture/stop Stops packet capture and flushes the current flow buffer.
GET /alerts Returns stored alerts from the database.
POST /system/retrain Starts retraining using analyst flagged false positives.
GET /system/threshold Returns the current detection threshold.

Checking the backend

When the backend is running, the readiness endpoint can be checked from a browser or a suitable HTTP client. 

http://127.0.0.1:9000/ready

A successful readiness response indicates that the backend has loaded the required model and can access the database.

Common startup problems

Model files are missing

Make sure the trained autoencoder and scaler files are present before starting the system.

Dashboard does not open in Docker

Check that Ubuntu has an active graphical session and that Docker has permission to access the display. The X11 display setting should also point to the active display.

Backend is not ready

Check the Docker logs and wait for the backend health check to complete. The dashboard depends on the backend being ready before normal operation can begin.

Network capture does not work

The capture service requires the permissions needed for raw network packet access. The Docker setup in the original project gives the backend the required network capabilities.

Basic operating procedure

  1. Start the backend and dashboard.
  2. Open the Sentinel Console.
  3. Select the network interface you want to monitor.
  4. Start packet capture.
  5. Observe incoming alerts on the console.
  6. Open suspicious events from the alert history.
  7. Review the feature values and anomaly score.
  8. Record analyst feedback when an alert is a false positive.
  9. Generate a forensic report when an investigation is complete.
